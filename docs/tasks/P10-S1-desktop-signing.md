## Goal
`release.yml` produces **signed** installers whenever the corresponding repository secrets exist and keeps producing the current unsigned ones when they do not (no secret may be required for the workflow to succeed). The Downloads page tells the visitor per OS whether the build is signed. Nothing here needs a real certificate to be developed: every signing step is conditional and unit-testable without one.

## Items (one commit each)
1. **macOS – Developer ID + notarization.** In the `release` job for the two macOS runners: when `secrets.APPLE_CERTIFICATE` is set, pass to tauri-action the env `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_TEAM_ID`, and for notarization `APPLE_API_ISSUER`, `APPLE_API_KEY`, `APPLE_API_KEY_PATH` (write the secret `APPLE_API_KEY_CONTENT` to `$RUNNER_TEMP/AuthKey.p8` in a step guarded by `if: env.HAS_APPLE == 'true'`; job-level `env: HAS_APPLE: ${{ secrets.APPLE_CERTIFICATE != '' }}`). Hardened runtime stays on (tauri default); add a minimal `bundle.macOS.entitlements` only if the webview needs one (test by reading Tauri's docs; do not guess). Document exactly which secret holds what and how the PM produces each value (`docs/signing.md`): base64 of the Developer ID Application `.p12`, its password, identity string "Developer ID Application: <name> (PM7LTV7M72)", the App Store Connect API key (issuer id, key id, `.p8` content).
2. **Windows – Authenticode.** Two conditional variants in the `windows-latest` build, both off without secrets: (a) PFX: secrets `WINDOWS_CERTIFICATE` (base64 PFX) + `WINDOWS_CERTIFICATE_PASSWORD` → import into the runner's certificate store, pass its thumbprint to Tauri (`bundle.windows.certificateThumbprint` via `--config` override or `TAURI_WINDOWS_SIGNTOOL_*`/the documented env – check Tauri 2.12 docs for the supported way), `digestAlgorithm` sha256, `timestampUrl` `http://timestamp.digicert.com`; (b) Azure Trusted Signing: secrets `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TRUSTED_SIGNING_ENDPOINT`, `AZURE_TRUSTED_SIGNING_ACCOUNT`, `AZURE_CERT_PROFILE` → `bundle.windows.signCommand` with `trusted-signing-cli` (install in the job). Both must sign the MSI, the NSIS installer and the app `.exe` inside them. Document both paths and what the owner must buy/set up (`docs/signing.md`: OV/EV certificate from a CA with cloud HSM, or Azure Trusted Signing – requirements, rough cost, which secrets result).
3. **Linux – GPG.** New job `sign-linux` (`needs: release`, ubuntu) that runs only when `secrets.GPG_PRIVATE_KEY` is set: import the key (`GPG_PASSPHRASE`), download the draft release's Linux assets (`.deb`, `.rpm`, `.AppImage`) with `gh release download`, create a detached ASCII signature `<asset>.asc` for each and upload them; additionally for **all** platforms: `SHA256SUMS` over every installer asset of the draft (file name + checksum, like `sha256sum`) and `SHA256SUMS.asc`; upload both. The public key is published as a repo file `keys/rusuite-release-key.asc` (the PM adds the real key; you add the path, a placeholder README in `keys/` and the deploy copy to `/rusuite-release-key.asc` on the portal in `scripts/deploy-web.sh` only if the file exists). Verify instructions in `docs/signing.md` and on the Downloads page (`gpg --verify`, `sha256sum -c`).
4. **`signing.json` asset + Downloads page.** A final job `signing-manifest` (`needs: [release, sign-linux]`, `if: always()`) uploads `signing.json` to the draft release: `{ "macos": {"signed": bool, "notarized": bool}, "windows": {"signed": bool, "method": "pfx"|"azure"|null}, "linux": {"gpg": bool, "fingerprint": "<from the key>"|null}, "sha256sums": bool }` derived from the job outputs. `scripts/gen-downloads.mjs` reads the asset from the release JSON it already fetches (fetch the asset body; absent = everything unsigned, as today) and renders per OS: signed → a short "Signed and notarized by Rusuite (Apple Developer ID)" / "Signed with an Authenticode certificate" / "GPG-signed – fingerprint … – verify: …" line instead of the Gatekeeper/SmartScreen steps; unsigned → the current texts. The page-level `portal.dl.unsigned.*` aside appears only if at least one OS is unsigned and names those OSes. Keys en+de. Unit tests in `gen-downloads.test.mjs` for all four combinations; the e2e Downloads tests keep passing (fixture releases with and without `signing.json`); `apps/portal/index.html` `portal.alpha` / `portal.soon.item8` texts are **not** changed here (P10-R1 does that when signing is live).
5. **`scripts/signing/asc.mjs`** (Node, no new dependencies – use `crypto` for ES256 JWT, `fetch`): App Store Connect API client reading `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_PATH` from the environment. Commands: `certificates list`, `certificates create --type DEVELOPER_ID_APPLICATION|IOS_DISTRIBUTION|DISTRIBUTION --csr <file> --out <cer>` (prints id + expiry, writes the DER cert), `bundle-ids list|register --id dev.rusuite.calc --name "Rusuite Calc" --platform IOS`, `profiles create --bundle-id <id> --type IOS_APP_STORE --certificate <certId> --out <file.mobileprovision>`, `profiles list`. Plus `scripts/signing/make-csr.sh` (openssl: 2048-bit RSA key + CSR with CN "Rusuite", C AT, writes to a directory the PM names – default `~/rusuite-signing/`), `scripts/signing/p12.sh <cer> <key> <out.p12>` (openssl pkcs12 export, password from `P12_PASSWORD` env) and `scripts/signing/gpg-key.sh` (generates the "Rusuite release key <release@rusuit.es>" with a passphrase from env, exports public key to `keys/`, prints fingerprint). Unit tests for the JWT builder and the request/response shaping with a mocked fetch. Never print secrets; redact in logs. **Do not call Apple** from tests.
6. **Docs.** `docs/signing.md` (overview of the three platforms, secrets table with name → content → how produced → which job uses it, owner shopping list for Windows, renewal dates, how to verify a download), `docs/release.md` (signing section replaced by a pointer + the extra assets `SHA256SUMS`, `*.asc`, `signing.json`), ROADMAP ideas in your report only.
