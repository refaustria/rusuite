# UI languages (P7-11)

The UI of Calc, Write, Show and the portal is available in **English** and **German**. Every user-visible string of the
UI lives in a catalog, so further languages only need new catalogs (and an entry in `LOCALES`).

## Choosing the language

- Default: the browser/webview language – `navigator.language` starting with `de` → German, anything else → English.
- The user's choice overrides it: **View › Language / Sprache** (a ribbon group in every app), the picker at the bottom of
  the **File** backstage, and the **EN / DE** switch of the portal. It is stored in `localStorage` under `rusuite.locale`.
  On the web the portal and the apps share one origin, so a choice made on the portal opens the apps in that language and
  vice versa; in the desktop shells the key lives in the webview's storage in the app data directory.
- Switching re-renders the open window in place (no reload, the document and its undo history stay) and sets
  `<html lang>`.

## Library (`packages/ui-shared/src/i18n/`, no runtime dependency)

| Export | |
| --- | --- |
| `createI18n({ locales: { en, de }, fallback: "en" })` | an `I18n` with `translate(locale, key, params?)`, `bind(locale)`, `has`, `extend` |
| `t(key, params?)` | translates in the current language (outside React, or in a component that called `useT`) |
| `useT()` | `t` bound to the current language; the component re-renders when it changes |
| `useLocale()`, `getLocale()`, `setLocale(l, { persist })`, `subscribeLocale` | the window's language |
| `<I18nProvider locale?>` | app root (`main.tsx`); with `locale` it forces a language without persisting it (tests) |
| `addMessages({ en, de })` | registers an app's catalogs on top of the shared ones (`apps/*/src/i18n.ts`) |
| `withLabel(base, key, params?)` | a constant option (paper size, number format, layout …) whose `label` is translated when read |
| `LanguageSelect`, `languageRibbonGroup(t)` | the "Language / Sprache" picker and its View-tab group |
| `formatNumber`, `formatDate`, `intlLocale` | `Intl` formatting of the UI chrome (status bars, recent list, presenter clock) |

Messages are flat, namespaced keys (`ribbon.file`, `backstage.saveAs`, `calc.fmt.title`, `show.order.bringToFront`) with
`{name}` placeholders. Plurals: `key.one` / `key.other`, chosen by `params.count` (`t("print.range.pages", { count })`).
Missing keys fall back to English, then to the key itself.

Catalogs: `packages/ui-shared/src/i18n/locales/{en,de}.json` (ribbon chrome, backstage, dialogs, print panel, formatting
controls, shared commands `cmd.*`, tab and group names `tab.*` / `group.*`), `apps/{calc,write,show}/src/locales/{en,de}.json`
(prefix `calc.` / `write.` / `show.`), `apps/portal/locales/{en,de}.json` (prefix `portal.`). Components import `t`/`useT`
from their app's `src/i18n.ts`, which registers the app catalog first.

Rules for new UI text:

1. Never write UI text as a literal: add the key to `en.json` **and** `de.json` and use `t("…")`.
2. A component that renders translated text calls `useT()` (memoised maps such as the shortcut map list `t` in their
   dependencies), so a language switch re-renders it.
3. Keep shortcuts as combo specs (`Mod+S`) and show them with `formatCombo`: German shows `Strg` (and `Entf`) like German
   Office, macOS shows `⌘`; the keys themselves do not change.

## Checks

- `pnpm i18n:check` (`scripts/i18n-check.mjs`, run in CI): catalog parity (`de.json` has exactly the keys and placeholders
  of `en.json`) for every package; no literal JSX text, `aria-label`, `title`, `placeholder`, `alt` or label props
  (`label`, `tooltip`, `confirmLabel`, …, `label:` in objects, sentence-like literals in conditions) in
  `packages/ui-shared/src` and `apps/{calc,write,show}/src`; every literal `t("key")` exists; every `data-i18n*` key of the
  portal exists. Allowed: brand names, file extensions, `fx`, shortcut combos, symbols; a line can opt out with
  `// i18n-ignore: <reason>`.
- A vitest test per package (`i18n.test.ts`) asserts the parity; `packages/ui-shared/src/i18n/i18n.test.tsx` covers
  interpolation, plurals, fallback, persistence, `<html lang>` and re-rendering; each app has a German render test.
- e2e (`packages/e2e/tests/i18n.spec.ts`): a German browser gets "Start" and "Speichern" in all three apps; View ›
  Language switches without a reload and survives one; the portal in German, its switch persisting and carrying over to
  Calc. `I18N_SHOTS=<dir>` saves screenshots of the German UI.

## Not translated (on purpose, for now)

- **Formula language**: function names stay English (`SUM`, not `SUMME`), the argument separator stays `,` and the decimal
  point `.`, error values stay `#REF!` etc. Calc's formula diagnostics (`apps/calc/src/formula/`) and the cores' error
  and info messages (Rust: parse errors, reader warnings, "Replaced 3 occurrences", cycle notes) stay English. Only the
  wrapper around a formula error ("… – fix or press Esc to discard") is translated.
- **Cell values**: number and date display in cells stays en-US (Format Cells previews included).
- **Document content**: placeholder prompts on slides and default names are UI (translated); text that ends up in a saved
  file (style ids, a pasted picture's name) is not.

A follow-up task may add locale-aware input/display and `;` separators if the owner wants it (see STATUS).

## Desktop file dialogs

The shells' `open_file_dialog` / `save_file` commands take an optional `dialog: { title, filterName }` from the UI
(`TauriBackend` passes "Open" / "Save As" and the app's file type, e.g. "Excel-Arbeitsmappe"); without it the dialog keeps the
platform title and the English filter name.


## Tone: informal in every language (owner rules 2026-10-16 for German, 2026-10-17 for all languages)

Every UI language addresses the user informally, like the German "du" (French "tu", Spanish "tú", Italian "tu", Dutch "je", Polish "ty", Swedish/Danish "du", Finnish "sinä" …). Never the polite form ("vous", "usted", "Lei", "u", "Pan/Pani", "Ön" …). The check below exists for German today; the languages task L0 of cycle 3.141 extends it per language.

### German

German addresses the user informally: **du / dich / dir / dein**, imperatives without "Sie" ("Wähle…", "Öffne…"). Never "Sie / Ihnen / Ihr(e)" as a form of address. `pnpm i18n:check` fails on formal forms in `de.json` values (P8-48): a capitalised `Sie`, `Ihnen`, `Ihr`, `Ihre`,
`Ihrem`, `Ihren`, `Ihrer` or `Ihres` anywhere in a value (`\b(Sie|Ihnen|Ihre?[mnrs]?)\b`, case-sensitive, so the
lower-case third-person "sie/ihr/ihre" is fine). For a genuine third-person use at the start of a sentence ("Sie werden
geleert" = "they are cleared") first try rewording ("Die Zellen werden geleert", lower case after a colon); if that is
not possible, add `"<locales dir>:<key>": "<reason>"` to `FORMAL_ALLOW` in `scripts/i18n-check.mjs` (for example
`"apps/calc/src/locales:calc.pivot.deleteConfirm.one": "Ihre = its cells"`). Entries whose value no longer matches are
reported as stale. The e2e German tests also assert that the backstage of each app and the portal show no formal form.
